# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**DeepMove** is a web-based HMI (Human-Machine Interface) for CNC machines (mills/routers) running **ESP32 + FluidNC** firmware. It is a fork of [ESP3D-WEBUI 3.0](https://github.com/luc-github/ESP3D-WEBUI) (via michmela44's fork) that has been stripped down and hardcoded to a single target/firmware combination: **CNC / FluidNC**. Unlike upstream ESP3D-WEBUI, this fork no longer supports selecting between printer/CNC/sand-table targets or multiple firmwares (Marlin, GRBL, etc.) at build time — `src/targets/index.ts` imports directly from `./CNC/FluidNC`.

It was designed for the [MillingStation](https://github.com/Meina88/MillingStation) controller but works with any ESP32 board running FluidNC. It supports **two firmware generations**: FluidNC 3.x (FluidMill, the maintainer's fork) and FluidNC 4.x (FluidStation) — they differ in ways that matter to the WebSocket and startup code, see "FluidNC 3.x vs 4.x" below before touching either.

The README (in Spanish) describes multi-target/multi-firmware npm scripts (`dev-<system>-<firmware>`, `buildall`, etc.) inherited from upstream documentation — **these no longer exist**. Use the actual scripts in `package.json` (below).

## Commands

```bash
npm install                 # install dependencies (Node LTS, see .nvmrc: 14.16.1 — CI uses Node 22.x)

npm run dev                 # starts the mock backend (server) + webpack-dev-server (front) concurrently
npm run server               # mock ESP32/FluidNC backend only: HTTP on :8080, WS on :8090 (config/server.js)
npm run front                # webpack-dev-server only, serves on http://localhost:8088, proxies to :8080

npm run build                # production build -> dist/ (index.html.gz + bundle analyzer reports)

npm run type-check           # tsc --noEmit
npm run lint                 # eslint src --ext .ts,.tsx
npm run lint:fix             # eslint --fix

npm run test                  # vitest run (co-located *.test.ts/*.test.tsx files)
npm run test:watch            # vitest, watch mode

npm run template              # regenerate reference translation templates in languages/ from src/**/translations/en.json
npm run buildlangpack -- <file>   # compress/package a single language file from languages/
npm run check -- reference=<path> target=<path>  # validate a language pack against the reference template
```

Tests are written with Vitest, co-located next to the source file they cover (`Foo.ts` → `Foo.test.ts`, no separate `__tests__` folder). Default test environment is `node`; add a `// @vitest-environment jsdom` pragma at the top of a test file when it touches the DOM (e.g. `window`, `document`, hook rendering via `@testing-library/preact`). CI (`.github/workflows/build-ci.yml`) only runs `npm install` and `npm run build` on push/PR — treat a clean `build`, `type-check`, and `test` as the bar for "does this work".

When developing, run `npm run dev` and open `http://localhost:8088`. The dev server (`config/server.js`) emulates the ESP32 HTTP endpoints and the two WebSocket channels (terminal/data) so the UI can run without real hardware; its mock filesystem lives under `server/CNC/FluidNC/{Flash,SD}`.

## Architecture

### Stack
Preact (not React) + TypeScript, Webpack 5, Sass/SCSS, spectre.css base styles with a custom neumorphic/industrial theme. `tsconfig.json` uses `jsxImportSource: preact`, strict mode is on. Prettier: no semicolons, 4-space indent, double quotes, 120 print width — see `.prettierrc`.

### Bootstrap and provider stack
Entry point is `src/index.js` → renders `<App />` (`src/components/App/index.tsx`). The app is a deep stack of context providers, outer to inner: `DatasContextProvider` → `TargetContextProvider` → `RouterContextProvider` → `UiContextProvider` → `HttpQueueContextProvider` → `SettingsContextProvider` → `ToastsContextProvider` → `ModalsContextProvider`. All contexts live in `src/contexts/` and are re-exported from `src/contexts/index.ts`. `App` also gates a `SafetyDisclaimerModal` behind a versioned localStorage flag (`deepmove_disclaimer_version`).

Below the providers, `ContentContainer` (`src/areas/index.tsx`) wires up the extension postMessage bridge (see below), kicks off the settings bootstrap (`getConnectionSettings` → `getInterfaceSettings`, i.e. `[ESP800]` then `preferences.json`/language/theme over the serial HTTP queue) and renders `ViewContainer` (`src/areas/ViewContainer.tsx`). `ViewContainer` shows `Menu` + `MainContainer` only when `canShowMainView` (`src/areas/viewState.ts`) is true — connected, not updating **and `ui.ready`** — and the `ConnectionContainer` otherwise (its "Connecting" spinner also covers the gap where the link is up but the settings are still loading). Do not gate the main view on `connected` alone: see "FluidNC 3.x vs 4.x" for why.

### Target/subtarget system
`src/targets/index.ts` imports `defaultPreferences` directly from the single `src/targets/CNC/FluidNC/preferences.json` file, and re-exports machine settings, panel list, icons, logos, and the `TargetContextProvider`/`useTargetContext` from `./CNC/FluidNC`. All CNC/FluidNC-specific UI, controls, styles and translations live under `src/targets/CNC/FluidNC/`. (Earlier versions merged three layered `preferences.json` files at runtime via a `mergeJSON` helper; that merge was collapsed into one file once the project settled on being permanently mono-target — if multi-target/firmware support is ever reintroduced, this is the seam to extend, and a merge layer can be reintroduced then.)

### Communication with the controller
Two parallel channels talk to the ESP32 controller, mirrored by the mock dev server:
- **HTTP** — `src/adapters/httpAdapter.tsx`, requests are queued through `HttpQueueContext` (`src/contexts/HttpQueueContext.tsx`) rather than fired directly.
- **WebSocket** — `src/Services/WebSocketService.ts` orchestrates a set of focused collaborators rather than doing everything itself: `ReconnectionManager.ts` (backoff/retries), `PingKeepAlive.ts` (ping/keep-alive, session-timeout detection), `SessionManager.ts` (`CURRENTID`/`ACTIVEID`), `CommandQueue.ts` (command queueing/sequencing, built on `Command`/`CommandState` in `src/Services/Commands/`), `LineBuffer.ts` (pure line-splitting on top of `WebSocketAdapter.ts`'s raw stream) and `webSocketUrl.ts` (builds the WS URL from what `[ESP800]` reports). System message parsing (`NOTIFICATION`, `ERROR`, `PING`, and `isControlMessage`) lives in `NotificationHandlers.ts`. `WebSocketAdapter` creates a **new** browser `WebSocket` on every `open()` after the previous one closed (a closed `WebSocket` can never be reopened); listeners live on the adapter and carry over. Protocol details (subprotocol `webui-v3`, message formats, the 3.x/4.x differences) are documented in `Memo/websocket.md`. `useWebSocketService` (`src/hooks/`) is the Preact-facing wrapper, and `ConnectionManager` (`src/components/ConnectionManager/`) is what actually calls `connect()` and re-arms polling after a reconnection.

Realtime G-code commands and the `[ESPnnn]` command family are documented in `Memo/Commands.md`, `Memo/realtimecmd.md`, and the `Memo/ESP3D [ESPxxx] format.md` files — consult these before changing command formatting/parsing.

### FluidNC 3.x vs 4.x (FluidMill vs FluidStation)
The UI was written and tuned against **FluidNC 3.x** (FluidMill). After moving to a **FluidNC 4.x** firmware (FluidStation) it became unstable: the dashboard came up blank on some loads ("panels don't load"), and any WebSocket drop left the UI dead until the page was reloaded. The causes were a set of protocol changes plus latent UI bugs that 3.x had happened to hide. They were identified by reading the UI and both firmware sources (the blank dashboard was never caught live in a debugger), and after the fix the symptoms are gone on a FluidStation board (2026-09). What differs, and what the UI does about it (wire-level detail in `Memo/websocket.md`):

| | FluidNC 3.x (FluidMill) | FluidNC 4.x (FluidStation) | UI handling |
|---|---|---|---|
| WS port / path | second server at HTTP port **+ 2**; `[ESP800]` reports that port | `AsyncWebSocket("/")` on the **HTTP port itself**; `[ESP800]` reports the HTTP port | `webSocketUrl.ts` always uses the reported `WebSocketPort`. The old `location.port + 2` guess was only right for 3.x (and the dev mock) |
| Session | a new WS disconnects every other one and broadcasts `activeID` (the old UI reacted with "already connected") | session = `sessionId` **cookie**; a new WS actively closes older WS with the same cookie; **no `activeID`** | a kicked page can't be told apart from a dropped link, so it reconnects — bounded, see below |
| Control messages | `currentID`, `PING:…` as text frames | plus `CURRENT_ID` and a bare `PING\n` every 10 s; all text, none (except `PING\n`) newline-terminated | `isControlMessage()`: never fed to the line buffer, or they get glued onto the next status report |
| HTTP while moving | `http_block_during_motion` (default **on**): every `[ESP…]`/`$/` command → 503, file requests → 503 | same setting and default, but `[ESP800]` is now exempt (so a cached page reload still gets its connection info); files → 503 page unless the browser has a cached copy | unchanged (firmware decision); `preferences.json`/language/theme failing falls back to defaults through the existing `onFail` |
| `/command` for G-code/realtime | `PAGEID` is **ignored** ("WebUI3 does not support PAGEID"): goes to the most recently used WS channel | `PAGEID` is honored: exact channel id, or the session cookie if absent; no such channel → 500 "WebSocket dead" | the stale `PAGEID` of a dead WS used to be masked on 3.x and now breaks every HTTP command — another reason a lost WS must recover |

**Startup race (the blank dashboard).** `WebSocketService.connect()` sets `connected: true` as soon as the socket opens, which is usually *before* `preferences.json` has come back over the serial HTTP queue. Until then `uisettings.current` is `undefined`, so `getValue()` returns `undefined` for everything, and the dashboard computes its initial visible panels **once** (`panels.initDone` latches) — with every `show`/`onstart` flag reading falsy it made nothing visible and never revisited it. Fixed on two levels: `canShowMainView` (main view waits for `ui.ready`) and `shouldInitPanels` (`src/pages/dashboard/panelsInit.ts`, dashboard init also waits for the settings). 3.x only worked by winning that race.

**WebSocket lifecycle** (all of it was effectively dead code before, since reconnection could never succeed):
- `WebSocketAdapter`: new native socket per `open()` once the old one is closing/closed; events from a replaced socket are ignored (a late `close` must not mark the new link closed); `open()` times out after 10 s instead of hanging in `CONNECTING`.
- `ReconnectionManager`: 4 attempts, 2 s apart; the retry timer clears itself when it fires (so `isPending()` is truthful); the attempt counter is **not** reset on connect but by `noteConnected()` after the link has stayed up 15 s. That is what stops two pages of one browser session (which kick each other on 4.x) from reconnecting forever — they give up after a few cycles. The old "one error counts as two attempts" quirk and `bumpAttempts()` are gone.
- `WebSocketService`: one failure is reported through several paths (socket `error`, `close`, failed `connect()`), so `_scheduleReconnection` does nothing while a retry is already pending; losing the link runs the same cleanup as a final disconnect (stop polling, clear modals, tell extensions); `connect()` registers its `close` listener once per native socket and ignores a `close` from a socket that is no longer current; `setReconnectedListener` fires after every connection but the first, and `ConnectionManager` uses it to call `useSettings().restartPolling` (polling is stopped on loss because HTTP polls have no WS channel to reach and would only toast errors).
- HTTP watchdog (`HttpQueueContext`, after 4 unanswered requests) calls `disconnect("connectionlost", false)` — `false` = do not mark it manual, otherwise the UI never reconnects.

**Dev mock:** `config/targets/CNC/FluidNC/index.js` now reports `WebSocketPort: "8090"` (the port `config/server.js` really listens on) because the UI no longer derives it from `location.port + 2`.

**Known open items** (deliberately not changed):
- With `http_block_during_motion` on (default, both firmwares), `[ESP…]` commands issued while moving fail with a 503 toast, and loading the UI mid-`Run` shows the firmware's own "Cannot load WebUI" page.
- The default `pollingcmds` (`preferences.json`) sends `?` over **HTTP every 100 ms**; both firmwares already auto-report status over the WS every 200 ms. Worth measuring/reducing on 4.x.
- `useSettings.getConnectionSettings` still derives the HTTP port for its "limited environment" (AP mode) modal as `WebSocketPort - 2`, which is wrong on 4.x.
- **Override-button lag** (+10%/-10% getting slower with each press during `Run`): the HTTP queue is strictly serial (`HttpQueueContext.executeHttpCall`), so N presses are N roundtrips. An attempt to send the realtime override byte straight over the WS (bypassing the queue) made things *worse* on the device and was reverted; no root cause was found. Note the original diagnosis (`Web_Server::poll()` sharing the poller task with auto-report) is a **3.x-only** mechanism — 4.x serves HTTP through `AsyncWebServer`. Measure the `/command` roundtrip during `Run` on 4.x before trying again. For the record, if it is retried: the firmware decodes realtime characters as UTF-8 with `PASS_THROUGH_80_BF`, so both `C2 9A` (what a WS text frame or the HTTP `%C2%9A` produces) and a raw `9A` byte are accepted on both firmwares; and a WS-side sender must not report success without knowing the socket accepted the frame, since +10% is not idempotent.

### Extension (iframe) API
`ContentContainer` (`src/areas/index.tsx`) calls `useExtensionBridge` (`src/areas/extensionBridge.ts`), which registers a `window.addEventListener("message", ...)` listener implementing a `postMessage`-based protocol for third-party iframe extensions (see `extensions/click2go`, `extensions/gcodeViewer` for real examples, `extensions_samples/` for templates). Message types: `cmd`, `query`, `upload`, `download`, `toast`, `modal`, `sound`, `translate`, `icon`, `extensionsData`, `capabilities`, `dispatch` — all handled in `extensionBridge.ts` except `modal` (dynamic field-form rendering + export/import of preferences), which is large enough to live in its own `src/areas/modalFieldsBridge.tsx`. Responses go back out via `dispatchToExtensions` (`src/components/Helpers`). Extensions are packaged/built independently (each has its own `package.json`/`webpack.config.js`) and are loaded into the main UI at runtime, not bundled by the main webpack build.

### UI composition
- `src/areas/` — top-level layout regions: `ViewContainer.tsx` (post-connection switch), `extensionBridge.ts`/`modalFieldsBridge.tsx` (extension IPC, see above), `menu.tsx` (nav), `connection.tsx` (pre-connect screen), `main.tsx` (main content switcher), `footer.tsx`, `elementsCache.tsx`.
- `src/components/Panels/` — the operational panels (Jog, Files, Terminal, Macros, Probe, Spindle/laser overrides, Status, Toolpath viewer, HMI mode, etc.) shown/hidden based on `UiContext` panel state and device size (phone/tablet/desktop — see README's "Filosofía" section: the UI deliberately shows only what's relevant to the current context rather than everything at once). Larger panels split their internal logic into a same-named sibling folder of hooks: `JogCNC.tsx` → `Panels/Jog/` (`useContinuousJog`, `useJogKeyboardShortcuts`, `useLaserFocus`), `Toolpath.tsx` → `Panels/Toolpath/` (`cameraMath.ts` + `useToolpathCamera`, `useCanvasRenderer`, `useToolpathViewPrefs`, `useToolPositionTracking`, `useToolpathFileEvents`, `decidePlayAction`) — not to be confused with `src/components/Toolpath/` below, the native rendering engine those hooks call into.
- `src/components/Controls/` — generic form/field primitives (`Field`, `FieldGroup`, etc.) used both by app UI and dynamically by the extension `modal`/`fields` protocol. `Field.tsx` is a discriminated union over each `Fields/*.tsx` component's own exported props type; most `Fields/*.tsx` components share their dependency-visibility and value-change-notification logic via `Fields/useFieldVisibility.ts` and `Fields/useNotifyValueChange.ts`.
- `src/tabs/` — settings tabs (machine, wifi, interface, features, about) with import/export helpers for preferences. The settings-tree node shape those tabs, `exportHelper.ts` and `Controls/Fields/ItemsList.tsx` all walk is the shared `PreferencesFieldData`/`PreferencesSection` type in `src/types/preferences.types.ts`.
- `src/components/Toolpath/` — the native G-code toolpath viewer/renderer engine itself, self-contained: `core/` (parser, modal state/interpreter, bounding box, toolpath model), `render/` (canvas renderer, projections, view presets, colors), `types/`. Public surface re-exported from `src/components/Toolpath/index.ts`. `GCodeParser.ts` (currently untracked/WIP) belongs here. (Not to be confused with `src/components/Panels/Toolpath/`, the `Toolpath.tsx` panel's own hooks — see above.)
- `src/hooks/` — cross-cutting hooks: `useHttpQueue`, `useSettings`, `useTargetCommands`, `useFilesManager`, `useWebSocketService`, `eventBus`.
- `src/contexts/Ui/` — `UiContext.tsx`'s internal collaborators (`audioEngine.ts`, `haptics.ts`, `usePanelsVisibility.ts`, `settingsTree.ts` for the `getValue`/`getElement` tree walk); the public surface stays `UiContextProvider`/`useUiContext`/`useUiContextFn` from `UiContext.tsx` itself.

### Translations
Translation JSON lives alongside the code it belongs to (`src/targets/translations/`, `src/targets/CNC/translations/`, `src/targets/CNC/FluidNC/translations/`), keyed by locale (`en.json`, etc.), and are combined with a plain object spread in `src/components/Translations/index.ts` (subtarget keys win over target, which win over base) — a different, simpler mechanism than the target/subtarget preferences system above, and one that was never `mergeJSON`-based even before that preferences merge was collapsed. `T()` (`src/components/Translations`) resolves keys at render time; `baseLangRessource` exposes the flattened resource for the extension `translate` message type. `npm run template` regenerates the canonical reference file in `languages/` from these `en.json` sources — run it after adding/renaming translation keys.

## Notes
- **HMI mode isn't a separate view** — there is no app-level "HMI mode" route or state. `HMIPanelElement` (`src/components/Panels/Hmi.tsx`) is just another entry in the same dashboard panels list as `JogPanelElement`, `ToolpathPanelElement`, etc. (`src/targets/CNC/FluidNC/panels.ts`), gated by the ordinary `showhmipanel` setting. What looks like a dedicated fullscreen HMI screen is the browser's native Fullscreen API called on that one panel's DOM node — the rest of the dashboard (and its other panels) stays mounted underneath unless something explicitly hides it. `Hmi.tsx` embeds its own instance of Jog/Files/Overrides/Terminal/Spindle/Probe/Toolpath (switched via `activeSection`, plus Toolpath always-on) — each a *second* live instance of a panel the dashboard may also have mounted. `useExclusiveFullscreenPanels` (`src/components/Panels/Hmi/`) hides every other dashboard panel for the duration of HMI fullscreen and restores them on exit, specifically to prevent two instances of the same panel running at once. Any future "panel that goes fullscreen and embeds others" should reuse this hook rather than reinvent it.
- `JogCNC.tsx`'s `currentFeedRate`/`currentAxis` are module-level singletons shared by every mounted `<JogPanel>` (there's no per-instance state) — this was a real bug before `useExclusiveFullscreenPanels` existed, since the standalone dashboard Jog panel and HMI's embedded one could both be alive at once. With HMI fullscreen now exclusive, only one `JogPanel` is ever mounted at a time, so the singleton is safe again by construction. Revisit only if some future layout deliberately shows two Jog UIs side by side.
- The bundle analyzer report/stats files at the repo root (`bundle-report-CNC-FluidNC.html`, `bundle-stats-CNC-FluidNC.json`) and everything in `dist/` are build output, not source — don't hand-edit them, they regenerate via `npm run build` / `analyze-bundle.js`.
- `Memo/` contains protocol and design notes (ESP command formats, websocket protocol, preferences/variables lists, feature notes) written by the maintainers — treat it as living reference documentation for the ESP3D/FluidNC protocol, not as a spec that's necessarily 100% in sync with code.
- `any` is repo-wide `warn` in `.eslintrc.json`, but ratcheted up to `error` for `src/contexts/**`, `src/components/Controls/**`, `src/targets/**`, `src/components/Panels/Jog/**`, and a handful of `src/Services/*.ts` collaborators (see the `overrides` block) — with a second `overrides` entry reverting specific still-not-fully-typed files back to `warn` (dynamic settings trees, extension-message payloads, `Field.tsx`'s discriminated-union escape hatches, the ambient module declarations, ...). Test files (`*.test.ts(x)`) are excluded from the strict tier entirely. When a file in that exceptions list gets fully typed, remove it from the list (don't just leave it); when cleaning up a new folder, extend the strict `files` list rather than loosening existing entries. `src/components/Controls/**` and `src/targets/**` are NOT fully clean as whole trees — most of the remaining `any` in the repo lives in exactly the files still listed in the exceptions override.
